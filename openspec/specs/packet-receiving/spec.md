## Purpose

Приём и разбор входящих пакетов адаптера MTRF-64-USB: как раскладывается 17-байтный пакет
в поля, что означает каждое поле в зависимости от режима, какие пакеты разбираются
в типизированные объекты и в каком порядке потребитель о них узнаёт.

## Requirements

### Requirement: Раскладка входящего пакета

Библиотека SHALL разбирать каждый входящий 17-байтный пакет в объект с полями: режим (байт 1),
результат (байт 2), байт TOGL (байт 3), канал (байт 4), команда (байт 5), формат данных (байт 6),
четыре байта данных (байты 7–10), 32-битный адрес устройства (байты 11–14, старший байт первым).

Библиотека MUST отклонять пакет неверной длины, без стартового маркера в байте 0 или без
стопового маркера в байте 16.

#### Scenario: Корректный пакет

- **WHEN** получен пакет длиной 17 байт со стартовым маркером 173 и стоповым 174
- **THEN** все поля доступны потребителю в разобранном виде

#### Scenario: Пакет с нарушенной рамкой

- **WHEN** длина не равна 17, либо байт 0 не равен 173, либо байт 16 не равен 174
- **THEN** разбор завершается ошибкой, объект не создаётся

### Requirement: Семантика байта TOGL зависит от режима

Байт 3 пакета SHALL быть доступен потребителю тремя способами, каждый со своей областью
применимости:

- **остаток пакетов ответа** — только для режимов TX и TXF: сколько пакетов ответа адаптер
  ещё передаст после этого (последний в серии → 0). Для режимов RX и RXF значение MUST быть
  «не применимо», а не ноль — ноль неотличим от честного «последний пакет»;
- **счётчик команд передатчика** — только для режимов RX и RXF: увеличивается на единицу
  при каждой новой команде передатчика; у повторов одной посылки значение одинаковое.
  Для режимов TX и TXF значение MUST быть «не применимо»;
- **сырой байт** — всегда, без интерпретации. Для режимов, семантику которых библиотека
  не знает (сервисный, обновление ПО), это единственный способ прочитать байт.

#### Scenario: Ответ на команду в режиме TXF

- **WHEN** получен пакет с режимом TXF и байтом 3, равным 2
- **THEN** остаток пакетов ответа равен 2
- **AND** счётчик команд передатчика — «не применимо»
- **AND** сырой байт равен 2

#### Scenario: Пакет от датчика в режиме RX

- **WHEN** получен пакет с режимом RX и байтом 3, равным 137
- **THEN** счётчик команд передатчика равен 137
- **AND** остаток пакетов ответа — «не применимо»
- **AND** сырой байт равен 137

#### Scenario: Повторная посылка датчика

- **WHEN** от одного передатчика в режиме RX подряд приходят два пакета с одинаковым байтом 3
- **THEN** у обоих счётчик команд передатчика одинаков — потребитель может опознать повтор

#### Scenario: Пакет в сервисном режиме

- **WHEN** получен пакет с режимом Service
- **THEN** и остаток пакетов, и счётчик команд — «не применимо»
- **AND** сырой байт доступен

### Requirement: Типизированный разбор состояния блока

Библиотека SHALL разбирать пакет с командой `Send_State` (130) и форматом данных **ровно 0**
в типизированный объект состояния блока nooLite-F:

- тип устройства — байт данных 0;
- версия прошивки — байт данных 1;
- состояние — биты 1–0 байта данных 2: `00` выключен, `01` включён, `10` включён на время;
- признак сервисного режима — бит 7 байта данных 2;
- уровень мощности — байт данных 3.

Объект состояния MUST создаваться только для формата 0: у него нет невалидных состояний
и признаков «данные не применимы» — если объект существует, его поля осмысленны.

Библиотека MUST NOT интерпретировать значения типа устройства и уровня мощности по таблице
из справки: реальные блоки возвращают значения, отличные от документированных (SUF-1-300
возвращает тип 5 и мощность 255, тогда как справка для SUF-1-300-A даёт 9 и 100). Эти поля
отдаются как есть.

#### Scenario: Блок включён

- **WHEN** получен `Send_State` с FMT=0 и байтами данных `[5, 0, 1, 255]`
- **THEN** тип устройства 5, версия прошивки 0, состояние «включён», не в сервисном режиме,
  уровень мощности 255

#### Scenario: Блок выключен

- **WHEN** получен `Send_State` с FMT=0 и байтами данных `[5, 0, 0, 0]`
- **THEN** состояние «выключен», уровень мощности 0

#### Scenario: Блок включён на время

- **WHEN** байт данных 2 имеет биты 1–0 равные `10`
- **THEN** состояние «включён на время»

#### Scenario: Блок в сервисном режиме

- **WHEN** бит 7 байта данных 2 установлен
- **THEN** признак сервисного режима — истина, состояние по битам 1–0 разбирается независимо

### Requirement: Ошибочный формат ответа состояния

Библиотека SHALL разбирать ответ `Send_State` с форматом данных **ровно 255** — блок так
отвечает на запрос несуществующей строки таблицы состояния — в **отдельный** типизированный
объект ошибки формата, не связанный с объектом состояния. Потребитель MUST NOT иметь
возможности перепутать ошибку с данными: это разные типы и разные события.

#### Scenario: Запрошена неизвестная строка

- **WHEN** получен `Send_State` с форматом данных 255
- **THEN** потребитель получает объект ошибки формата
- **AND** объект состояния для этого пакета не создаётся

### Requirement: Прочие строки таблицы состояния не типизируются

`Send_State` с форматом данных, отличным от 0 и 255 (иные строки таблицы состояния,
например 16, 17, 18), библиотека SHALL публиковать **только** в общем виде — сырым пакетом
через общее событие. Ни объект состояния, ни объект ошибки для таких пакетов MUST NOT
создаваться.

Библиотека типизирует только те форматы, раскладку которых знает; остальные потребитель
разбирает сам, зная, какую строку запрашивал.

#### Scenario: Ответ на запрос строки 16

- **WHEN** получен `Send_State` с форматом данных 16
- **THEN** срабатывает только общее событие с сырым пакетом
- **AND** ни событие состояния, ни событие ошибки формата не срабатывают

### Requirement: Типизированный разбор данных микроклимата

Библиотека SHALL разбирать пакет с командой `Sens_Temp_Humi` (21) и форматом данных 7
в типизированный объект: температура (12-битное знаковое число в десятых долях градуса
из байтов данных 0–1), влажность (байт данных 2, только для датчиков типа PT111 —
биты 6–4 байта данных 1 равны `010`; иначе «нет данных»), признак разряда батареи
(бит 7 байта данных 1).

#### Scenario: Показания PT111

- **WHEN** получен пакет с командой 21, FMT=7 и байтами данных `[134, 33, 26, …]`
- **THEN** температура 39,0 °C, влажность 26 %, батарея в норме

#### Scenario: Отрицательная температура

- **WHEN** 12-битное значение температуры больше или равно 0x800
- **THEN** оно интерпретируется как отрицательное в дополнительном коде

### Requirement: Порядок публикации входящих пакетов

Для каждого принятого пакета библиотека SHALL сначала опубликовать его в общем виде
(событие для всех пакетов), а затем — если пакет разбирается в типизированный объект —
опубликовать типизированный объект отдельным событием.

Потребитель, подписанный только на общее событие, MUST получать все пакеты, включая те,
для которых есть типизированный разбор.

#### Scenario: Пакет состояния блока

- **WHEN** принят `Send_State` с FMT=0
- **THEN** сначала срабатывает общее событие с пакетом, затем событие состояния блока
  с типизированным объектом

#### Scenario: Пакет ошибки формата

- **WHEN** принят `Send_State` с FMT=255
- **THEN** сначала срабатывает общее событие с пакетом, затем событие ошибки формата

#### Scenario: Пакет микроклимата

- **WHEN** принят пакет с командой 21 и FMT=7
- **THEN** сначала срабатывает общее событие, затем событие микроклимата

#### Scenario: Пакет без типизированного разбора

- **WHEN** принят пакет, для которого типизированного разбора нет (например, ответ адаптера
  на выход из сервисного режима)
- **THEN** срабатывает только общее событие

### Requirement: Обработчик события не блокирует приём и отправку

Библиотека SHALL вызывать обработчики событий входящих пакетов вне критической секции,
в которой выполняются чтение из порта, запись команд и открытие/закрытие порта. Длительность
работы обработчика MUST NOT влиять на приём следующих пакетов из порта, на отправку команд
из других потоков и на закрытие адаптера.

Пакеты MUST доходить до обработчиков в том порядке, в каком они приняты из порта; обработчики
одного пакета MUST вызываться последовательно, а не параллельно.

#### Scenario: Медленный обработчик и отправка

- **WHEN** обработчик события выполняется дольше периода опроса порта, а другой поток в это
  время вызывает отправку команды
- **THEN** отправка выполняется, не дожидаясь завершения обработчика

#### Scenario: Медленный обработчик и приём

- **WHEN** обработчик события выполняется, а в порт приходят новые пакеты
- **THEN** новые пакеты вычитываются из порта и ставятся в очередь, не дожидаясь обработчика
- **AND** после завершения обработчика они доходят до обработчиков в порядке прихода

#### Scenario: Порядок при нескольких пакетах

- **WHEN** из порта приняты пакеты A, B, C подряд
- **THEN** обработчики получают A, затем B, затем C — независимо от того, сколько времени
  занял каждый

### Requirement: Изоляция обработчиков

Исключение в одном обработчике события MUST NOT препятствовать вызову остальных обработчиков
того же пакета, обработке следующих пакетов и работе адаптера. Такое исключение SHALL быть
доставлено потребителю через событие ошибки. Исключение внутри самого обработчика ошибки
SHALL быть подавлено — иначе один сбойный обработчик остановил бы доставку всех событий.

#### Scenario: Обработчик бросил исключение

- **WHEN** обработчик общего события бросил исключение для пакета, у которого есть
  типизированный разбор
- **THEN** исключение доставляется через событие ошибки
- **AND** типизированное событие для того же пакета всё равно вызывается
- **AND** следующие пакеты обрабатываются

#### Scenario: Обработчик ошибки бросил исключение

- **WHEN** обработчик события ошибки сам бросил исключение
- **THEN** оно подавляется, доставка событий продолжается

### Requirement: Ограниченная очередь входящих пакетов

Принятые из порта пакеты SHALL накапливаться в очереди ограниченной ёмкости, задаваемой при
создании адаптера; ёмкость по умолчанию — 128 пакетов. При переполнении библиотека SHALL
отбрасывать **самый старый** пакет из очереди, освобождая место для нового: свежее состояние
ценнее истории. Число отброшенных пакетов SHALL быть доступно потребителю через счётчик.

Постановка пакета в очередь MUST NOT блокировать поток чтения — переполнение разрешается
отбрасыванием, а не ожиданием.

#### Scenario: Очередь переполнена

- **WHEN** очередь заполнена, а из порта принят ещё один пакет
- **THEN** самый старый пакет очереди отбрасывается, новый ставится в конец
- **AND** счётчик отброшенных увеличивается на единицу
- **AND** поток чтения не блокируется

#### Scenario: Ёмкость по умолчанию

- **WHEN** адаптер создан без указания ёмкости очереди
- **THEN** ёмкость равна 128

### Requirement: Закрытие адаптера и судьба очереди

Библиотека SHALL предоставлять два способа закрытия, различающиеся судьбой ещё не обработанных
пакетов:

- **немедленное** — порт закрывается сразу, необработанные пакеты **отбрасываются**, событие
  отключения вызывается, вызов возвращается. Это поведение по умолчанию и поведение при
  освобождении адаптера (`Dispose`): после закрытия состояние потребителя может быть
  непригодно для обработчиков, и библиотека не может этого знать;
- **с обработкой остатка** — порт закрывается так же сразу (новых пакетов не поступает),
  но вызов дожидается, пока все уже принятые пакеты будут доставлены обработчикам, затем
  вызывает событие отключения и возвращается. По возврату очередь MUST быть пуста.
  Отмена ожидания через токен отмены — остаток отбрасывается.

В обоих случаях событие отключения MUST быть последним событием адаптера: после него
обработчики входящих пакетов не вызываются.

Вызов закрытия с обработкой остатка изнутри обработчика события MUST завершаться исключением:
иначе диспетчер ждал бы завершения самого себя.

#### Scenario: Немедленное закрытие с непустой очередью

- **WHEN** в очереди лежат необработанные пакеты и вызвано немедленное закрытие
- **THEN** порт закрыт, эти пакеты не доходят до обработчиков, событие отключения вызвано
- **AND** после события отключения обработчики входящих пакетов не вызываются

#### Scenario: Закрытие с обработкой остатка

- **WHEN** в очереди лежат необработанные пакеты и вызвано закрытие с обработкой остатка
- **THEN** порт закрыт немедленно
- **AND** все пакеты из очереди доходят до обработчиков в порядке прихода
- **AND** затем вызывается событие отключения, затем вызов возвращается

#### Scenario: Отмена ожидания

- **WHEN** закрытие с обработкой остатка ожидает медленный обработчик, а токен отмены сработал
- **THEN** ожидание прерывается, остаток очереди отбрасывается, порт остаётся закрытым

#### Scenario: Закрытие с обработкой остатка из обработчика

- **WHEN** обработчик события пакета вызывает закрытие с обработкой остатка и синхронно ждёт
  его завершения
- **THEN** вызов завершается исключением, а не взаимной блокировкой

#### Scenario: Освобождение адаптера

- **WHEN** адаптер освобождается (`Dispose`) с непустой очередью
- **THEN** поведение как при немедленном закрытии: остаток отбрасывается
