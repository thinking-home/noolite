## Context

Мотивация — см. `proposal.md` → «Why». Здесь только состояние и ограничения, влияющие на подход.

Текущее состояние сборки:

| Что | Сейчас | Целевое |
|---|---|---|
| TFM всех 4 проектов | `net9.0` | `net10.0` |
| `global.json` | `sdk.version = 9.0.100`, без `rollForward` | `10.0.100` + `rollForward` |
| SDK на машине разработки | — | установлен только `10.0.400` |
| Рантаймы на машине | — | только `Microsoft.NETCore.App 10.0.11` |
| `System.IO.Ports` | 9.0.1 | 10.0.11 |
| `McMaster.Extensions.CommandLineUtils` | 4.1.1 | 5.1.0 (мажор) |
| `xunit` | 2.9.3 (последняя версия этого пакета) | пакет `xunit.v3` 4.0.0 |
| `xunit.runner.visualstudio` | 3.0.1 | 4.0.0 (мажор) |
| `Microsoft.NET.Test.Sdk` | 17.12.0 | 18.3.0 (мажор) |
| `FakeItEasy` | 8.3.0 | удаляется |
| `actions/checkout` | v3 | v7 |
| `actions/setup-dotnet` | v2 | v6 |

Ограничения, которые формируют подход:

- Репозиторий сейчас не собирается локально: `global.json` требует SDK 9.0.100, установлен только
  10.0.400. Базовой зелёной сборки для сравнения нет.
- Кодовая база маленькая (~700 строк библиотеки, 4 тестовых файла), логика — побайтовая сборка
  17-байтных пакетов и `SerialPort`. Языковых конструкций, чувствительных к смене TFM, нет;
  основной риск лежит не в коде, а в мажорах пакетов тестового стека и CLI.
- Тесты используют минимальный срез xUnit: только `[Fact]` и `Assert.Equal / Null / True / False /
  Contains / ThrowsAny` из namespace `Xunit`. Ни `[Theory]`, ни фикстур, ни кастомных атрибутов.
- `FakeItEasy` объявлен в `.Tests.csproj`, но ни в одном тестовом файле не используется.
  В библиотеке нет ни одного `unsafe`/`stackalloc`/`fixed`, хотя `AllowUnsafeBlocks` включён.
- `DebugConsole/Program.cs` захардкожен под macOS-порт `/dev/tty.usbserial-AL00HDFI` и канал 13;
  после `return;` на строке 72 идёт недостижимый код, а большая часть сценариев (привязка,
  отвязка, очистка каналов, адресная отправка по ID) существует в виде закомментированных блоков.
  На Windows (`COMx`) программа в текущем виде неработоспособна.
- В CLI `noolite` нет команды «слушать порт»: приём входящих пакетов от датчиков доступен только
  через `DebugConsole` (события `ReceiveData` / `ReceiveMicroclimateData`).

## Goals / Non-Goals

**Goals:**

- Все четыре проекта собираются и тестируются на SDK 10.0.x, все зависимости — на актуальных
  версиях, включая мажорные переходы.
- Обновление делается так, чтобы при поломке было понятно, какой именно пакет виноват, и был
  заранее описанный откат.
- Репозиторий чистится от неиспользуемого: пакет без применения, мёртвая настройка компилятора,
  дубль в `Package.xml`.
- `DebugConsole` превращается в пригодный для работы отладочный инструмент с режимами — он же
  становится инструментом e2e-приёмки.
- Переезд подтверждается на живом железе: не только «собирается и тесты зелёные», но и
  «адаптер отвечает, реле щёлкает, пакет от датчика приходит».

**Non-Goals:**

- Изменение публичного API библиотеки, версии пакета (остаётся 4.4.0) и публикация в NuGet.
- Переезд тестов на `xunit.v3` / Microsoft.Testing.Platform — вынесен в отдельный change
  (см. Decision 3).
- Потокобезопасность `SendCommand`, обёртки `Read_State`/`Send_State`, async-приём — следующие
  change'и.
- Превращение `DebugConsole` в законченный продукт: это отладочный инструмент, он не пакуется
  и не публикуется, к его CLI не предъявляются требования уровня `noolite`.
- Добавление команды «слушать» в публичный CLI `noolite` — расширение поверхности dotnet tool
  не относится к переезду.

## Decisions

### 1. Один TFM `net10.0`, без мультитаргетинга

**Решение:** `<TargetFramework>net10.0</TargetFramework>` во всех четырёх проектах.

**Альтернатива:** `<TargetFrameworks>net9.0;net10.0</TargetFrameworks>` в библиотеке, чтобы не
ронять потребителей на net9.0.

**Почему так:** единственный известный потребитель — драйвер для `ThinkingHome.DeviceModel`,
он на .NET 10; опубликованная 4.4.0 остаётся в NuGet для тех, кто на net9.0. Мультитаргет
удваивает матрицу сборки и прогона тестов ради гипотетических потребителей, а в будущих
change'ах (async-приём) может ещё и потребовать `#if` по TFM.

### 2. `global.json`: `10.0.100` + `rollForward: latestFeature`

**Решение:**

```json
{ "sdk": { "version": "10.0.100", "rollForward": "latestFeature" } }
```

**Альтернатива:** прописать точную установленную версию `10.0.400` (поведение по умолчанию —
`latestPatch`).

**Почему так:** ровно на эти грабли репозиторий и наступил сейчас. По умолчанию `rollForward`
равен `latestPatch`, то есть feature-band фиксируется: запись `10.0.100` без `rollForward`
**не примет** установленный 10.0.400 — воспроизвели бы ту же ошибку на следующем обновлении SDK.
`latestFeature` разрешает любой 10.0.x (100/200/300/400…), но не пускает 11.x.

### 3. Тестовый стек остаётся на VSTest (решение пересмотрено по факту реализации)

**Исходное решение:** заменить пакет `xunit` 2.9.3 на `xunit.v3` 4.0.0, `xunit.runner.visualstudio`
→ 4.0.0, `Microsoft.NET.Test.Sdk` → 18.3.0.

**Что выяснилось при реализации:** переезд оказался не сменой пакета, а сменой платформы запуска
тестов. `xunit.v3` 4.0.0 по умолчанию несёт **MTP v2** (поддержка MTP v1 удалена начиная с 4.0.0),
а под .NET 10 SDK запуск MTP в VSTest-режиме удалён — `dotnet test` падает с

```
error : Testing with VSTest target is no longer supported by Microsoft.Testing.Platform
on .NET 10 SDK and later.
```

Обходной MSBuild-флаг `TestingPlatformDotnetTestSupport` работает только до MTP v1, то есть для
нас недоступен. Единственный путь — MTP-режим `dotnet test`, включаемый секцией `test`
в `global.json`. Он был проверен и работает: 18 тестов, **правок в тестовых файлах не потребовалось
вовсе**. Под MTP также становятся не нужны `Microsoft.NET.Test.Sdk` (хост VSTest) и
`xunit.runner.visualstudio` (адаптер VSTest) — без них те же 18 тестов проходят.

**Итоговое решение владельца:** тестовые пакеты **не обновлять**. Остаются `xunit` 2.9.3,
`xunit.runner.visualstudio` 3.0.1, `Microsoft.NET.Test.Sdk` 17.12.0. Проверено: на net10.0 этот
стек собирается с нулём предупреждений и даёт те же 18 зелёных тестов.

**Почему так:** цена переезда — не правки в тестах (их ноль), а хвост сопутствующих изменений:
секция `test` в `global.json`, переписывание CI-команды под MTP-синтаксис (`dotnet test --project`,
`-f` не применяется) и неопределённость с обнаружением тестов в Rider — у JetBrains открыта
задача RSRP-498837 «поддержка обнаружения MTP-тестов без `Microsoft.NET.Test.Sdk`».
Сама документация xUnit советует держать оба VSTest-пакета «until you can be certain that all
your supported versions of your development environments are using MTP».

**Что принимается как долг:** `xunit` 2.9.3 — последняя версия своего пакета, поколение
заморожено. VSTest не объявлен устаревшим и остаётся режимом `dotnet test` по умолчанию, но
новый опыт .NET 10 SDK сделан под MTP. Переезд предстоит, и его стоит делать отдельным change'ем,
пока тесты используют минимальный срез API — сейчас он мигрирует без единой правки в исходниках.

### 4. `McMaster.Extensions.CommandLineUtils` → 5.1.0

**Решение:** обновить до 5.1.0; при поломке — зафиксировать, что именно сломалось, и чинить
`Console/Program.cs`, а не откатывать пакет.

**Почему риск приемлем:** по nuspec 5.1.0 таргетит net472 и net8.0 — подключается к net10.0
штатно; релиз-ноты 5.1 содержат только фичи и фиксы. `Console/Program.cs` использует
устоявшийся срез API (`CommandLineApplication`, `CommandArgument<T>`, `CommandOption`,
`OnExecute`, `HelpOption`, `ShowHelp`, `CommandParsingException`), который в 5.x сохранён.
Основной риск — в самом переходе 4→5 (отброшенные старые TFM, возможные изменения дефолтов),
и он проверяется запуском `noolite --help` и `noolite ports`.

### 5. Удаляем неиспользуемое, но не трогаем «неиспользуемое на вид»

**Решение:** удалить ссылку на `FakeItEasy`, свойство `AllowUnsafeBlocks` и дублирующуюся
строку `<PackageRequireLicenseAcceptance>` в `Package.xml`.

**Почему это безопасно:** по каждому пункту есть проверяемый факт — `A.Fake`/`A.CallTo` не
встречаются ни в одном файле; `unsafe`/`stackalloc`/`fixed` не встречаются ни в одном файле;
дубль свойства MSBuild — это буквально одна и та же строка дважды.

**Что НЕ удаляем:** закомментированные и недостижимые сценарии в `DebugConsole` — они выглядят
мусором, но описывают реальные кейсы использования консоли. Они переезжают в режимы (Decision 6).

### 6. `DebugConsole` — режимы, задаваемые параметром

**Решение:** первый аргумент — имя режима, дальше параметры режима; порт, канал и ID устройства
передаются аргументами. Во всех режимах, работающих с адаптером, подписка на `ReceiveData` /
`ReceiveMicroclimateData` / `Connect` / `Disconnect` / `Error` активна и все входящие пакеты
печатаются — иначе не видно ответов адаптера.

Минимальный набор режимов, покрывающий существующие (в том числе закомментированные) сценарии:

| Режим | Что делает | Откуда взят |
|---|---|---|
| `ports` | список COM-портов | строка 12 |
| `listen` | открыть порт, `ExitServiceMode`, печатать входящие пакеты до прерывания | события + `ReceiveMicroclimateData` |
| `on` / `off` / `switch` | `On`/`Off`/`Switch` и `*F`-варианты по каналу, опционально адресно по ID | строки 52–69, 101–117 |
| `bind` / `unbind` | `Bind`/`BindF`, `Unbind`/`UnbindF` по каналу | строки 47–50, 82–99 |
| `bind-rx` | `BindStart`/`BindStop` — привязка датчиков в режиме RX | `MTRFXXAdapterExtensions` |
| `clear` / `clear-all` | `ClearChannel` по каналу / `ClearAllChannels` | строки 74–77 |

**Разбор аргументов — вручную, без `McMaster`.** Альтернатива — подключить `McMaster` и в
отладочный проект, как в `Console`. Не берём: это добавляет зависимость в проект, который
существует ровно для того, чтобы быстро потыкать адаптер, и связывает отладку с мажорным
обновлением CLI-парсера, которое в этом же change'е проверяется. Разбор двух-трёх позиционных
аргументов и флага `-f` того не стоит.

**Точный список режимов и синтаксис уточняются при реализации** — таблица выше задаёт нижнюю
границу покрытия, а не финальный интерфейс.

### 7. Порядок работ: параметризация консоли и baseline — ДО переезда

**Решение:**

1. `global.json` (иначе не работает вообще ничего);
2. установка .NET 9 **Runtime**;
3. режимы `DebugConsole` — **на net9.0**;
4. baseline e2e на живом адаптере — **на net9.0**;
5. смена TFM на net10.0 → промежуточная зелёная точка на старых версиях пакетов;
6. обновление пакетов по одному, с прогоном тестов после каждого;
7. удаление неиспользуемого;
8. сборка, тесты, dotnet tool;
9. повторный e2e теми же сценариями → сравнение с baseline;
10. CI.

**Почему baseline снимается до переезда и той же программой:** сравнивать «до/после» имеет смысл
только если инструмент один и тот же. Если параметризовать консоль после переезда, то при
расхождении поведения нельзя будет отличить «сломал переезд» от «новый режим написан иначе, чем
старый хардкод». Отсюда же требование поставить рантайм: собрать net9.0 умеет и SDK 10
(down-level targeting), а вот **запустить** net9.0-приложение без `Microsoft.NETCore.App 9.0.x`
нельзя.

**Почему Runtime, а не SDK 9:** SDK 9 не нужен — компилировать net9.0 умеет SDK 10. Ставить SDK
ради одного прогона значит добавить на машину вторую цепочку инструментов и ещё один источник
расхождений в `global.json`.

**Почему промежуточная зелёная точка на шаге 5:** если после смены TFM всё собирается на старых
пакетах, то любая последующая поломка однозначно относится к конкретному пакету, а не к
смене TFM.

### 8. Приёмка: четыре независимых критерия

1. `dotnet build -c Release` без ошибок; новые предупреждения — зафиксированы;
2. `dotnet test` — все тесты проходят, число тестов не меньше зафиксированного baseline;
3. `dotnet pack` → `dotnet tool install --global` → `noolite --help` и `noolite ports` →
   `dotnet tool uninstall --global`;
4. e2e на живом адаптере: связь (`listen` — адаптер отвечает после `ExitServiceMode`),
   управление (`on`/`off` реально переключают силовой блок), приём (пакет от датчика приходит
   и печатается) — все три сценария совпадают с baseline.
5. CI-workflow зелёный.

**Почему `--help` и `ports` для tool-проверки:** обе команды не открывают порт, но реально
прогоняют загрузку сборки, `McMaster` 5.x и `System.IO.Ports` 10.x из установленного пакета —
то есть проверяют ровно то, что могло сломаться при смене рантайма и мажорах.

## Risks / Trade-offs

- **`Microsoft.NET.Test.Sdk` 18.x меняет платформу запуска тестов (VSTest → MTP)** → откат на
  17.14.1 предусмотрен как штатный вариант; обновляется последним в тестовом стеке, чтобы его
  поломка не смешивалась с переездом на `xunit.v3`.
- **`xunit.v3` — смена поколения фреймворка** → тесты используют минимальный срез API, но если
  правки выйдут за косметические, шаг откатывается на `xunit` 2.9.3 и переезд выносится
  в отдельный change; это фиксируется в отчёте.
- **`McMaster` 5.x — мажор под всем CLI** → проверяется `noolite --help` / `noolite ports`;
  при поломке чиним `Console/Program.cs`.
- **e2e физически переключает силовой блок** → сценарий выполняется совместно с владельцем,
  на заранее названном канале и порту; в baseline и в финальной проверке используется один и
  тот же блок и один и тот же канал.
- **Если .NET 9 Runtime не будет установлен** → baseline e2e не снимается; тогда e2e после
  переезда становится единственной точкой, и при неудаче нельзя будет отличить регрессию от
  изначально неверной конфигурации железа. Этот исход фиксируется явно, а не замалчивается.
- **Смена TFM ломает потребителей на net9.0** → осознанный размен (Decision 1); пакет 4.4.0
  остаётся в NuGet, публикации net10-версии в этом change нет.
- **Мажоры GitHub Actions (`checkout` v3→v7, `setup-dotnet` v2→v6)** проверяются только на CI →
  CI-шаг делается последним и отдельным коммитом.
- **`DebugConsole` переписывается целиком** → это отладочный инструмент, не пакуется и не
  публикуется; риск ограничен самим инструментом, но он же используется в приёмке, поэтому его
  корректность подтверждается baseline-прогоном ещё на net9.0.
