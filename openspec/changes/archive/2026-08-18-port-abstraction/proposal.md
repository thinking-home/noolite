## Why

`MTRFXXAdapter` создаёт `System.IO.Ports.SerialPort` прямо в конструкторе, поэтому самая сложная
часть библиотеки — замок отправки, очередь и диспетчер приёма, `Close` / `FlushAndCloseAsync` —
не покрыта юнит-тестами: единственный способ проверить её сегодня — живой адаптер на COM3
и одноразовые режимы DebugConsole (уже удалены). Регрессию в замке, порядке событий или
закрытии ничто не поймает.

Это запланированный следующий шаг после `async-receive` («точка расширения + тесты»):
проверки диспетчера с живого железа переезжают в юнит-тесты.

## What Changes

**Внутренний шов над `SerialPort` — только для тестов.**

- `internal`-интерфейс порта с ровно теми операциями, которые использует адаптер:
  открыть/закрыть, признак «открыт», число доступных байтов, чтение байта и блока байтов,
  запись блока байтов.
- `internal`-перегрузка конструктора `MTRFXXAdapter(<порт>, queueCapacity = 128)`. Публичный
  конструктор `MTRFXXAdapter(string portName, …)` остаётся и делегирует ей, создавая
  `internal`-обёртку над `SerialPort` (9600 бод, ограниченное время записи — как сейчас).
- `InternalsVisibleTo("ThinkingHome.NooLite.Tests")` в `.csproj` библиотеки.
- **Публичная поверхность не меняется.** Ни одного нового публичного типа или члена;
  наблюдаемое поведение адаптера — то же.

Это схема из откаченного `thread-safe-send` (архивный `report.md`, разделы 2 и 4),
воспроизводимая целиком.

**Тесты на адаптер через подставной порт** (в проекте `ThinkingHome.NooLite.Tests`):

- атомарность записи из многих потоков и проброс ошибки записи;
- диспетчер: порядок пакетов, общее событие → типизированное, изоляция обработчиков,
  обработчик не блокирует отправку и приём, битый пакет → `Error`;
- ограниченная очередь: отбрасывание нового при переполнении, счётчик, порядок;
- закрытие: `Close` с непустой очередью, `FlushAndCloseAsync` (доставка остатка, отмена,
  вызов изнутри обработчика), `Dispose`, повторный `Open`, ошибка чтения → `Error` + закрытие;
- цепочка расширений `ReadStateF` → `SendCommand` → байты в порту (сейчас в
  `ReadStateCommandTests` покрыт только `BuildCommand`).

**Явно вне объёма:**

- публичная точка расширения (свой транспорт потребителя) — не в этом change'е; если
  понадобится, интерфейс можно открыть позже отдельным решением;
- освобождение порта (`SerialPort.Dispose`) адаптером — существующее поведение
  (порт только закрывается) не меняется, интерфейс без `Dispose`; отдельная тема;
- изменение поведения адаптера по итогам тестов: если тест выявит расхождение кода со спекой,
  оно фиксируется в отчёте как находка, решение о правке — за владельцем;
- реконнект, корреляция, модель устройств — драйвер.

## Capabilities

### New Capabilities

Нет.

### Modified Capabilities

Нет. Наблюдаемое поведение не меняется — шов internal, тесты проверяют существующие
требования `command-sending` и `packet-receiving` как есть. Change объявляет `skip_specs: true`.

Один тест (ошибка чтения из порта → `Error` + закрытие адаптера) проверяет существующее
поведение, которого нет ни в одной спеке; помечен в design как «спекой не описано».
Записать его требованием в `packet-receiving` можно отдельно, если понадобится.

## Impact

- **Код библиотеки**: `internal`-интерфейс порта и `internal`-обёртка над `SerialPort`
  (два файла в `Internal/`); `MTRFXXAdapter.cs` — тип поля порта, второй (`internal`)
  конструктор, константы 9600 / таймаут записи переезжают в обёртку; `InternalsVisibleTo`
  в `.csproj`. Логика адаптера (замок, таймер, очередь, диспетчер, закрытие) не меняется.
- **Публичное API**: без изменений. `VersionPrefix` не меняется.
- **Тесты**: подставной порт и ~30 новых тестов; существующие 35 не меняются.
  Тесты асинхронные по природе (таймер 50 мс, диспетчер в пуле) — должны быть устойчивыми:
  ожидание по событиям с таймаутом, без фиксированных `Sleep` в проверках.
- **Console / DebugConsole**: без изменений.
- **Документация**: README не меняется (публичного API не прибавилось);
  `openspec/config.yaml` → `context` — снять «известное ограничение: тестов на адаптер нет».
- **Проверка на железе**: регрессия `on` / `off` / `state` / `listen` на COM3 —
  убедиться, что обёртка ведёт себя как прежний прямой `SerialPort`.
