## Context

Мотивация — `proposal.md` → «Why». Проверяемые требования — `openspec/specs/command-sending`,
`openspec/specs/packet-receiving`; собственной спеки у change'а нет (`skip_specs`: наблюдаемое
поведение не меняется).

Что есть сейчас (`MTRFXXAdapter.cs`):

- поле `private readonly SerialPort device`, создаётся в конструкторе:
  `new SerialPort(portName, 9600) { WriteTimeout = WRITE_TIMEOUT }`;
- адаптер использует у порта ровно: `IsOpen`, `BytesToRead`, `Open()`, `Close()`, `ReadByte()`,
  `Read(byte[], int, int)`, `Write(byte[], int, int)`. `WriteTimeout` — только при создании.
  `Dispose` порта не вызывается (известное наблюдение из `thread-safe-send/report.md`);
- вся логика (замок, таймер 50 мс, `Channel<byte[]>`, диспетчер, `closing`/`inFlight`/`drained`,
  `Close`/`FlushAndCloseAsync`/`Dispose`) не зависит от того, что именно за `device`, — ей нужен
  только перечисленный набор операций.

Схема шва и теста на конкурентную запись уже была реализована и откачена
(`archive/2026-08-16-thread-safe-send/report.md`, разделы 2 и 4): `internal interface ISerialDevice`,
`internal sealed SerialPortDevice`, внутренний конструктор, `InternalsVisibleTo`, `FakeSerialDevice`
с `Thread.Yield()` между байтами. Тест со снятым замком падал — схема рабочая. Здесь она
воспроизводится как есть и достраивается тестами на диспетчер и закрытие.

Тесты — xUnit 2.9, 35 существующих тестов на разбор байтов; классы по умолчанию выполняются
параллельно.

## Goals / Non-Goals

**Goals:**

- Публичная поверхность не меняется: всё новое — `internal`.
- Логика адаптера не переписывается — меняется только тип поля и способ его получения.
- Тесты детерминированы: ожидание по сигналам с таймаутом, а не по фиксированным паузам;
  падение теста означает дефект, а не медленную машину.
- Каждый тест адаптера привязан к сценарию спеки (`command-sending`, `packet-receiving`) либо
  явно помечен как проверка существующего поведения, спекой не описанного.

**Non-Goals:**

- Публичная точка расширения (свой транспорт) — не здесь.
- Событийное чтение вместо таймера, `ReadAsync`, `IAsyncEnumerable` — не трогаем.
- `Dispose` порта адаптером — вне объёма (proposal).
- Исправление поведения адаптера по находкам тестов — фиксируется, не делается молча.

## Decisions

### 1. `internal interface ISerialDevice` с семью членами, без `WriteTimeout` и `Dispose`

```csharp
namespace ThinkingHome.NooLite.Internal;

internal interface ISerialDevice
{
    bool IsOpen { get; }
    int BytesToRead { get; }
    void Open();
    void Close();
    int ReadByte();
    int Read(byte[] buffer, int offset, int count);
    void Write(byte[] buffer, int offset, int count);
}
```

Сигнатуры повторяют `SerialPort` один в один — обёртка тривиальна, подставной порт в тестах
пишется по знакомой семантике. Критерий состава — «ровно те члены, которые использует адаптер»
(как в `thread-safe-send`).

**`WriteTimeout` не в интерфейсе.** Адаптер выставляет его один раз при создании порта;
это параметр транспорта того же рода, что и 9600 бод. Обе константы переезжают в обёртку
`SerialPortDevice`; подставному порту таймаут не нужен.

**`Dispose` не в интерфейсе.** Адаптер порт не освобождает и сейчас; не расширяем.

Имя и namespace — как в откаченной реализации (`ISerialDevice`, поле `device` в адаптере,
`ThinkingHome.NooLite.Internal`).

### 2. `SerialPortDevice` — `internal sealed`, тонкая обёртка

Конструктор `(string portName)` создаёт `new SerialPort(portName, BAUD_RATE) { WriteTimeout =
WRITE_TIMEOUT }`; константы `9600` и `500` переезжают сюда вместе с комментарием о причине
таймаута (запись под тем же замком, что чтение). Каждый член делегирует одноимённому члену
`SerialPort`. Логики нет — тестировать в ней нечего; её работа проверяется на железе (задача 8.1).

### 3. Два конструктора: публичный строковый делегирует внутреннему

```csharp
public MTRFXXAdapter(string portName, int queueCapacity = DEFAULT_QUEUE_CAPACITY)
    : this(new SerialPortDevice(portName), queueCapacity) { }

internal MTRFXXAdapter(ISerialDevice device, int queueCapacity = DEFAULT_QUEUE_CAPACITY)
{
    ArgumentNullException.ThrowIfNull(device);
    if (queueCapacity < 1) throw new ArgumentOutOfRangeException(...);   // как сейчас
    this.device = device;
    ...
}
```

Поле — `private readonly ISerialDevice device`; всё остальное тело конструктора (таймер, канал,
`Task.Run(DispatchAsync)`) без изменений. `ThreadSafeExec`, `TryRead`, `SendCommand`, `Open`,
`Close`, `FlushAndCloseAsync` компилируются как есть — они используют только члены интерфейса.

`InternalsVisibleTo("ThinkingHome.NooLite.Tests")` — в `.csproj` библиотеки
(`<InternalsVisibleTo Include="..."/>`), как в откаченной реализации.

Порядок проверок в строковом конструкторе меняется незначительно: раньше `queueCapacity`
проверялся до создания `SerialPort`, теперь `SerialPortDevice(portName)` создаётся первым.
`SerialPort` при создании порт не открывает; при `portName == null` он и раньше бросал
`ArgumentNullException` — наблюдаемого отличия нет.

Для внешнего кода перегрузка невидима, поэтому неоднозначности `new MTRFXXAdapter(null)`
у потребителей нет; внутри проекта тестов литерал `null` придётся типизировать
(`(ISerialDevice)null`) — только в тесте на `ArgumentNullException`.

### 4. Подставной порт `FakeSerialDevice` в проекте тестов

Один класс на все тесты адаптера, `ThinkingHome.NooLite.Tests/FakeSerialDevice.cs`:

- **входящие**: потокобезопасный буфер байтов; `Feed(params byte[][] packets)` добавляет байты
  (вызывается из потока теста, читается из потока таймера — замок внутри). `BytesToRead` —
  длина буфера, `ReadByte`/`Read` вынимают с начала;
- **исходящие**: общий журнал байтов; `Write` копирует байты **по одному** с `Thread.Yield()`
  между ними — расширяет окно гонки до величины, которую планировщик ловит надёжно
  (проверено в `thread-safe-send`: без замка тест падал на стартовом маркере);
  `WrittenPackets` режет журнал на срезы по 17;
- **состояние**: `Open`/`Close` переключают `IsOpen`; `Write` при `IsOpen == false` бросает
  `InvalidOperationException` — как `SerialPort`; на этом держится сценарий «Отправка при закрытом
  порту» из `command-sending`;
- **отказы по требованию**: `FailRead = ex` — следующий `BytesToRead` бросает `ex`;
  `FailWrite = ex` — `Write` бросает `ex`. Так проверяются «ошибка записи → исключение
  вызывающему» и «ошибка чтения → `Error` + закрытие».

Пакеты для входящих собираются существующим `TestHelpers.GetBytes()` / `Set(...)`
(маркеры 173/174 уже там); для типизированных нужны байты 5 (команда), 6 (формат), 7–10 (данные).

### 5. Тесты ждут сигналов, а не спят

Адаптер опрашивает порт раз в 50 мс, диспетчер работает в пуле — тест не может проверять
результат синхронно после `Feed`. Правила:

- **положительные проверки** («событие пришло», «метод вернулся») — ждать сигнал с таймаутом
  (5 с): `TaskCompletionSource` / `SemaphoreSlim` в обработчике, `Task.WaitAsync(timeout)`
  для методов. Истечение таймаута = падение теста с понятным сообщением;
- **«медленный обработчик»** — обработчик ждёт `ManualResetEventSlim`, который тест отпускает
  явно; плюс сигнал «обработчик начался», чтобы тест точно знал, что пакет уже вынут из очереди
  (важно для тестов очереди: P1 в обработке, ёмкость считается от P2);
- **отрицательные проверки** («после `Disconnect` обработчики не вызывались», «пакет
  не доставлен») — единственное место, где нужна пауза: после положительного сигнала
  (`Disconnect` пришёл, обработчик отпущен) подождать ≥ 4 периода опроса (200 мс) и проверить,
  что счётчик не вырос. Слабее положительной проверки — принимается, таких тестов мало;
- **изоляция от параллельных классов**: тесты адаптера — в одной xUnit-коллекции
  (`[Collection("adapter")]`), чтобы нагрузочный тест записи (8 потоков) не съедал время
  у тестов с таймаутами. Остальные 35 тестов на разбор — как были;
- **никаких `Thread.Sleep` в роли проверки** — только внутри `FakeSerialDevice.Write`
  (`Yield`) и в отрицательных проверках выше.

## Risks / Trade-offs

- **Тест обнажит расхождение со спекой: `Close()` во время обработчика.** `closing`
  проверяется один раз перед `Dispatch(bytes)`; если `Close()` пришёл, пока обработчик
  `ReceiveData` пакета выполняется, типизированное событие **того же пакета** сработает после
  `Disconnect`. Спека говорит «после отключения обработчики входящих пакетов не вызываются».
  → Тесты закрытия используют для P1 пакет без типизированного разбора, чтобы проверять ровно
  спековый сценарий («в очереди лежат необработанные пакеты»); краевой случай записывается
  в отчёт с вариантами (проверять `closing` перед каждым `Raise`; либо принять как «обработчики
  уже начатого пакета доигрывают» и уточнить спеку). Решение — за владельцем, здесь не делается.
- **Флаки по времени** (таймер 50 мс, пул потоков, CI под нагрузкой). → Decision 5:
  сигналы с таймаутом 5 с, коллекция без параллелизма, отрицательные проверки — только после
  положительного сигнала. Если тест всё же мигает — это дефект теста, чинится увеличением
  таймаута или заменой паузы на сигнал, а не `Retry`.
- **`InternalsVisibleTo` открывает тестам всё `internal`** библиотеки, не только шов. → Тесты
  используют только `ISerialDevice` и внутренний конструктор; это дисциплина ревью, не механика.
- **Порядок валидации в строковом конструкторе** — Decision 3, наблюдаемого отличия нет.
- **`SerialPort` по-прежнему не освобождается** — вне объёма, остаётся как было.

## Migration Plan

Не требуется: публичное API не меняется, существующие вызовы `new MTRFXXAdapter(port)`
компилируются и работают как прежде. Откат — `git revert` одного change'а: тесты и два новых
файла удаляются, адаптер возвращается к прямому `SerialPort`.
