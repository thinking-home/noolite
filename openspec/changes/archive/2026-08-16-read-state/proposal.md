## Why

Драйверу NooLite для хаба `ThinkingHome.DeviceModel` нужно **опрашивать состояние** блоков
nooLite-F и **читать ответы типизированно**. Сейчас в библиотеке есть коды команд `ReadState = 128`,
`SendState = 130`, но обёрток нет — потребитель вынужден вручную собирать `SendCommand` с сырыми
enum'ами, а ответ `Send_State` разбирать по байтам сам, зная раскладку FMT=0 наизусть. Для
`MicroclimateData` такой типизированный разбор уже существует — для состояния блока его нет.

Второе: `ReceivedData.Remains` **обнуляется** для пакетов режима RX/RXF
(`ReceivedData.cs:37`). Байт TOGL для RX — это счётчик новых команд передатчика, по которому
драйвер обязан дедуплицировать повторные посылки датчиков (передатчики шлют каждую посылку
несколько раз). Сейчас этот счётчик через публичное API недоступен вообще; подтверждено
на живом железе — у пакетов PT-111 всегда `remains: 0`.

## What Changes

**Обёртка `ReadState`** в `MTRFXXAdapterExtensions`, по образцу существующих `OnF`/`OffF`:

- по каналу — ответят все привязанные к каналу блоки, каждый своим `Send_State`;
- адресно по ID блока (`CTR=8`, `MTRFXXAction.SendTargetedCommand`);
- параметр FMT — адрес строки таблицы состояния, по умолчанию 0 (основная информация).

**Типизированный разбор `Send_State`** — два класса-наследника `ReceivedData` по образцу
`MicroclimateData` и **два события**, каждое строго под свой формат:

- **данные состояния** (FMT=0): тип устройства (D0), версия прошивки (D1), состояние
  (D2, биты 1–0: выключен / включён / включён на время; бит 7 — сервисный режим), уровень
  мощности (D3). У объекта нет невалидных состояний — он создаётся только для FMT=0;
- **ошибка формата** (FMT=255): блок так отвечает на запрос несуществующей строки таблицы.
  Отдельный тип и отдельное событие — потребитель не может перепутать ошибку с данными.

`Send_State` с любым другим FMT (прочие строки таблицы, например 16/17/18) типизированно
**не публикуется** — только через общее `ReceiveData` сырым пакетом. Библиотека типизирует
то, что знает; остальное потребитель разбирает сам, зная, какую строку запрашивал.

Оба события срабатывают после `ReceiveData`, по образцу `ReceiveMicroclimateData`.

**Три свойства над байтом TOGL** в `ReceivedData` — по решению владельца, «правильный вариант,
а не простой»:

- `Remains: int?` — только для TX/TXF: сколько пакетов ответа осталось. Для RX/RXF — `null`
  (было `0`, что неотличимо от честного «последний пакет»). **BREAKING** — тип меняется
  с `int` на `int?`.
- `ToggleCounter: int?` — только для RX/RXF: счётчик новых команд передатчика. Для TX/TXF — `null`.
- `Togl: byte` — сырой байт всегда. Для режимов Service и Update руководство смысл байта
  не описывает; сырой доступ оставляет потребителю выход.

`ToString()` обновляется, чтобы показывать применимое свойство, а не `remains: 0` для датчиков.

Явно вне объёма:

- **`VersionPrefix` не меняется** — мажорный релиз владелец делает сам, отдельно.
- `WriteState` (FMT 16/17/18) — драйверу на первом шаге не нужен.
- Async-приём — следующий change.
- Корреляция запрос↔ответ, ожидание конкретного `Send_State` на конкретный `ReadState` —
  драйвер, по принятому разделению ответственности.

## Capabilities

### New Capabilities

- `packet-receiving`: приём и разбор входящих пакетов адаптера — общая раскладка `ReceivedData`
  (включая семантику байта TOGL по режимам), типизированные разборы для микроклимата
  и состояния блока, порядок и условия публикации событий.

Организация спек, заложенная в предыдущем change'е: `command-sending` (отправка, уже есть),
`packet-receiving` (этот change), `adapter-connection` (жизненный цикл — позже, если понадобится).

### Modified Capabilities

- `command-sending`: добавляется требование к обёртке `ReadState` — какие пакеты она
  формирует по каналу и адресно, с каким FMT.

## Impact

- **Код**: `ThinkingHome.NooLite/ReceivedData.cs` (три свойства, `ToString`), два новых класса
  разбора (данные состояния, ошибка формата) и enum состояния, `MTRFXXAdapterExtensions.cs`
  (обёртка), `MTRFXXAdapter.cs` (два новых события и их публикация в `TryRead`).
- **Публичное API**: **BREAKING** в `ReceivedData.Remains` (`int` → `int?`); остальное — только
  добавления (свойства, классы, события, методы-расширения).
- **Тесты**: разбор состояния — по образцу `MicroclimateData/ParseTest.cs`; три свойства над TOGL —
  по образцу `ReceivedData/ParseTests.cs`. Всё это чистый разбор байтов, шов не нужен.
- **Проверка на железе**: послать `ReadState` на канал 0 и адресно на ID 33347 — получить
  разобранный ответ от SUF-1-300. Здесь же зафиксировать реальные значения D0/D3 для этого
  блока: в handoff для SUF-1-300-A указано D0=9 и D3=100 в релейном режиме, а с железа пришло
  D0=5 и D3=255 — разбор не должен опираться на константы из справки.
- **DebugConsole**: режим `state <port> <channel> [-f] [--id N]` — иначе e2e делать нечем.
- **Документация**: `README.md` → раздел API, добавить `ReadState` и описание разбора состояния.
