## Context

Мотивация — `proposal.md` → «Why». Требования — `specs/packet-receiving/spec.md`
и `specs/command-sending/spec.md`. Здесь только то, что нужно для объяснения подхода.

Существующие образцы, на которые опирается change:

- `MicroclimateData : ReceivedData` — типизированный разбор поверх сырого пакета: конструктор
  принимает те же 17 байт, свойства вычисляются из `Data1..Data4`, `ToString()` дополняет базовый.
  Публикуется отдельным событием `ReceiveMicroclimateData` **после** `ReceiveData`, по условию
  «команда 21 и FMT 7» прямо в `TryRead`.
- `MTRFXXAdapterExtensions` — все обёртки идут через приватные `Send`/`SendData`, которые
  по `useFMode` и `deviceId` выбирают режим и действие: `deviceId == null` → CTR=0,
  `deviceId == 0` → CTR=1 (широковещательно), иначе CTR=8. Формат данных передаётся явно.
- `ReceivedData.Remains` сейчас `int`, для RX/RXF возвращает 0 — заглушка вместо семантики.

Наблюдения с железа (архивный `report.md` change'а `update-to-net10`), которые ограничивают
дизайн разбора состояния:

- SUF-1-300 в ответ на `On`/`Off` присылает `Send_State` FMT=0 с `[5, 0, 1, 255]` / `[5, 0, 0, 0]`;
- D0 = 5, тогда как в справке для SUF-1-300-A — 9; D3 = 255, тогда как справка для релейного
  режима даёт 100. Константы из справки на реальном блоке не сходятся.

## Goals / Non-Goals

**Goals:**

- Драйвер вызывает `ReadStateF(channel)` / `ReadStateF(channel, deviceId)` и получает
  типизированный объект состояния через событие — без ручной сборки пакета и разбора байтов.
- Байт TOGL доступен драйверу честно: остаток для TXF, счётчик для RX, сырой байт всегда.
- Всё, что относится к разбору, покрыто юнит-тестами — это чистые функции над байтами.
- Поведение подтверждено на живом блоке SUF-1-300.

**Non-Goals:**

- Ожидание ответа на конкретный запрос, тайм-ауты, сопоставление «этот `Send_State` — ответ
  на тот `Read_State`» — драйвер.
- Async-приём — следующий change; здесь остаются события.
- Таблица типов устройств и интерпретация мощности по типу — библиотека отдаёт числа как есть.
- `WriteState` и разбор FMT ≠ 0.
- Мажорный релиз — владелец делает сам, `VersionPrefix` не трогаем.

## Decisions

### 1. Три свойства над байтом 3, ни одно не врёт

**Решение:** в `ReceivedData`:

```csharp
public byte Togl => data[3];                                   // всегда
public int? Remains => IsTx ? data[3] : null;                 // TX, TXF
public int? ToggleCounter => IsRx ? data[3] : null;           // RX, RXF
```

где `IsTx` — режимы TX и TXF, `IsRx` — RX и RXF. Для Service и Update оба типизированных
свойства `null`, доступен только `Togl`.

**Альтернатива A:** оставить `Remains: int` как есть (0 для RX), добавить только `Togl`.
Совместимо, но `Remains == 0` у RX-пакета продолжает читаться как «последний пакет ответа» —
ложь под видом числа.

**Альтернатива B:** убрать условие, `Remains => data[3]` всегда. Одно свойство, но у датчика
`Remains == 137` — бессмыслица.

**Почему так:** байт хранит две разные величины в зависимости от режима, и единственный
способ не врать — дать каждой своё имя и `null` там, где понятие не применимо. `null`, а не 0
и не исключение: 0 неотличим от честного значения, а исключение из геттера ломает `ToString()`
и отладочные дампы. Ломающее изменение (`int` → `int?`) владелец принял осознанно —
мажорный релиз будет отдельно.

**Именование:** `Togl` — как в руководстве, чтобы искалось по документации; `ToggleCounter` —
потому что руководство называет байт TOGL именно из-за «переключения» счётчика при новой команде.
Doc-комментарий на каждом свойстве говорит, для каких режимов оно осмысленно.

### 2. Два типа для `Send_State`: данные и ошибка, без невалидных состояний

**Решение (владельца):** два класса-наследника `ReceivedData`, каждый строго под свой FMT.

Данные состояния — только FMT=0:

```csharp
public class PowerUnitStateData : ReceivedData
{
    public byte DeviceType => Data1;
    public byte FirmwareVersion => Data2;
    public PowerUnitState State => (PowerUnitState)(Data3 & 0b11);
    public bool ServiceMode => (Data3 & 0b1000_0000) != 0;
    public byte PowerLevel => Data4;
}
```

Ошибка формата — только FMT=255:

```csharp
public class StateFormatErrorData : ReceivedData
{
    // без дополнительных свойств: сам факт объекта — и есть ошибка;
    // DataFormat, канал, ID устройства доступны из базового класса
}
```

и enum `PowerUnitState { Off = 0, On = 1, TemporaryOn = 2 }`.

**Альтернативы, которые рассматривались и отклонены:**

- *один класс с `IsFormatError` и публикация для любого FMT* — у объекта появляются невалидные
  состояния: при FMT ≠ 0 свойства `State`/`DeviceType` вычислимы, но бессмысленны; потребитель
  обязан помнить о проверке `DataFormat`. Ловушка;
- *один класс с nullable-свойствами* (`State: PowerUnitState?`, `null` при FMT ≠ 0) — ловушку
  снимает компилятор, но объект по-прежнему смешивает данные и ошибку в одном типе.

**Почему два типа лучше:** у `PowerUnitStateData` нет ни одного поля, которое могло бы быть
«не применимо» — если объект существует, все его свойства осмысленны. Ошибка — отдельный
тип, спутать её с данными невозможно ни на уровне типов, ни на уровне событий. Это тот же
принцип, что принят для TOGL: одно имя — одна семантика.

**Почему `DeviceType` и `PowerLevel` — голые байты:** справка даёт для SUF-1-300-A тип 9
и мощность 100 в релейном режиме; живой SUF-1-300 отдаёт 5 и 255. Заведи мы enum типов
или интерпретацию «100 = реле», первый же реальный блок оказался бы «неизвестным». Числа
как есть — это честно, а маппинг в понятные названия — задача драйвера, у которого есть
контекст (какие блоки в системе).

**Почему `State` — enum из трёх значений, а биты 1–0 могут дать `11`:** значение `11`
руководством не описано. Приведение `(PowerUnitState)3` даст неименованное значение enum'а —
это видно в отладке и не роняет разбор. Не заводим `Unknown = 3`, чтобы не выдумывать семантику.

### 3. Публикация — два события, строго по FMT; прочие строки — только сырым пакетом

**Решение (владельца):**

```csharp
public event Action<object, PowerUnitStateData> ReceivePowerUnitState;   // FMT == 0
public event Action<object, StateFormatErrorData> ReceiveStateFormatError; // FMT == 255
```

В `TryRead` после `ReceiveData`:

```csharp
if (data.Command == MTRFXXCommand.SendState)
{
    if (data.DataFormat == 0)
        ReceivePowerUnitState?.Invoke(this, new PowerUnitStateData(bytes));
    else if (data.DataFormat == 255)
        ReceiveStateFormatError?.Invoke(this, new StateFormatErrorData(bytes));
    // прочие FMT: только ReceiveData, типизации нет
}
```

**Что с FMT ∉ {0, 255}** — другими строками таблицы (16/17/18 и любыми прочими): они доходят
до потребителя **только через `ReceiveData`** сырым пакетом. Библиотека типизирует ровно то,
раскладку чего знает. Потребитель, запросивший строку 16, знает, что запрашивал, и разбирает
`Data1..Data4` сам.

**Отклонённые варианты для прочих строк:**

- *публиковать в событие ошибки* — легитимный ответ на запрос строки 16 пришёл бы как «ошибка»,
  название вводит в заблуждение;
- *третье событие «сырая строка»* — три события на одну команду; полно, но избыточно, пока
  библиотека не знает раскладку ни одной строки, кроме 0.

**Цена решения:** потребитель, который слушает только типизированные события, не увидит ответы
на запросы других строк. Это осознанно: он их и не должен слать без знания раскладки; а если
шлёт — подпишется на `ReceiveData`.

**Почему не переиспользовать `ReceiveData` с проверкой типа:** потребитель мог бы делать
`if (data is PowerUnitStateData)`, но для этого `TryRead` должен создавать наследника вместо
`ReceivedData` — а это меняет тип объекта в существующем событии. Отдельные события — по образцу
микроклимата, никаких сюрпризов для существующих подписчиков.

### 4. Обёртка — через существующий `Send`

**Решение:** в `MTRFXXAdapterExtensions`:

```csharp
public static void ReadStateF(this MTRFXXAdapter adapter, byte channel,
    uint? deviceId = null, byte format = 0)
{
    SendData(adapter, MTRFXXCommand.ReadState, true, channel, deviceId,
        (MTRFXXDataFormat)format);
}
```

`SendData` уже умеет выбрать CTR=0 / CTR=1 / CTR=8 по `deviceId`. FMT — это адрес строки,
а не один из именованных форматов, поэтому параметр `byte` с приведением к enum'у.

**Только F-вариант.** `Read_State` — команда двусторонней связи; классические блоки не отвечают
и запрос по TX бессмыслен. Не-F перегрузки, в отличие от `On`/`Off`, здесь не будет.

**`deviceId == 0` даст CTR=1** — широковещательный запрос: по протоколу после него адаптер
сам опросит блоки канала. Это существующее поведение `GetModeAndAction`, оно применимо
и здесь — оставляем, отражаем в doc-комментарии.

### 5. Проверка

**Юнит-тесты — на весь разбор**, шов не нужен, это чистые функции над байтами:

- три свойства TOGL × четыре режима (TX, TXF, RX, RXF) + Service;
- `PowerUnitStateData`: включён / выключен / включён на время / сервисный бит / биты `11`;
- `StateFormatErrorData`: создаётся из пакета с FMT=255, базовые поля доступны;
- `ReadStateF`: `BuildCommand` даёт нужные MODE, CTR, CMD, FMT, ID — по каналу и адресно
  (`BuildCommand` статический и публичный).

Ветвление публикации в `TryRead` (0 → данные, 255 → ошибка, иное → ничего) юнит-тестом
не покрывается — оно живёт в адаптере, где нет шва. Проверяется на железе.

**На железе:** режим `state` в `DebugConsole` — послать `ReadStateF` на канал 0 и адресно
на 33347, увидеть `PowerUnitStateData`; запросить строку 200 — увидеть `StateFormatErrorData`
(если блок отвечает FMT=255 — иначе зафиксировать, чем именно). Сверить D0/D3 с наблюдениями
из `update-to-net10`.

## Risks / Trade-offs

- **`Remains: int` → `int?` ломает компиляцию потребителей.** Принято осознанно; мажор
  владелец делает отдельно. До релиза библиотека в состоянии «код 5.0, версия 4.4.0» — коммитить
  можно, публиковать нельзя.
- **Ответы на запросы строк ≠ 0/255 не типизируются** — доходят только через `ReceiveData`.
  Потребитель, слушающий одни типизированные события, их не увидит. Осознанно: библиотека
  типизирует то, что знает; drive-by-разбор чужих строк — на потребителе.
- **Значения `State` вне 0–2** — enum примет неименованное значение. Не выдумываем `Unknown`,
  оставляем как есть.
- **`Send_State` приходит и без запроса** — после любой команды в TXF (`On`, `Off`, …). Событие
  `ReceivePowerUnitState` будет срабатывать чаще, чем потребитель вызывает `ReadStateF`. Это
  протокол, а не дефект; в doc-комментарии события — сказать явно.
- **Ветвление по FMT в `TryRead` не покрыто юнит-тестом** — там нет шва. Проверка на железе
  покрывает FMT=0 надёжно; FMT=255 — только если блок действительно так отвечает на неизвестную
  строку (справка это утверждает, на нашем блоке не проверялось).
