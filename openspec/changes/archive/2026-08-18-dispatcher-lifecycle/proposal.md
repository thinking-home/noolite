## Why

Жизненный цикл адаптера сейчас размазан по нескольким полям, каждое из которых закрывает
отдельную гонку, найденную при реализации `async-receive`: `closing` (не начинать пакеты после
`Disconnect`), `inFlight` (очередь пуста, но обработчик ещё работает), `drained` (сигнал «остаток
доставлен»). Корректность держится на порядке записей в разных потоках — «`inFlight`
поднимается **до** `TryRead`, иначе окно», «`drained` обнуляется в `finally`» — и этот порядок
живёт только в комментариях. Добавление нового требования означает новый флаг и новую проверку
в ещё одном месте.

Прямое следствие этой конструкции — незакрытый краевой случай из `port-abstraction`
(`report.md` → «Находки»): `closing` проверяется один раз перед разбором пакета, поэтому если
`Close()` приходит, пока выполняется обработчик, типизированное событие **того же пакета**
срабатывает **после** `Disconnect`. Спека требует «после отключения — тишина»; сейчас это не
выполняется, и одной проверкой флага не чинится.

## What Changes

**Управление жизненным циклом переходит диспетчеру.** `Close` / `FlushAndCloseAsync` / `Dispose`
больше не трогают очередь и не вызывают `Disconnect` сами: они синхронно закрывают порт и
останавливают таймер (как сейчас), затем публикуют запрос закрытия, который диспетчер
обрабатывает в порядке своей очереди. Отбрасывание остатка, доставка остатка и вызов
`Disconnect` — теперь в потоке диспетчера.

- **`Disconnect` становится асинхронным для `Close()` / `Dispose()`.** **BREAKING (поведение):**
  `Close()` возвращается сразу после закрытия порта, **не дожидаясь** `Disconnect` — событие
  приходит вскоре из потока доставки. Потребитель, полагавшийся на «после возврата `Close()`
  событие `Disconnect` уже было», должен подписаться на событие. Так решено владельцем.
- **`FlushAndCloseAsync` — как раньше:** ждёт доставки остатка и `Disconnect`; по возврату
  очередь пуста и отключение уже произошло; из обработчика — `InvalidOperationException`.
- **Краевой случай исправляется.** `Disconnect` вызывается диспетчером между пакетами, поэтому
  обработчики уже начатого пакета (включая типизированные события) доводятся до конца **до**
  отключения, а после него ни один обработчик входящего пакета не вызывается. «Отключение —
  последнее событие» становится верным по построению, а не по охране флагом.
- **`Close()` изнутри обработчика становится безопасным** — он лишь публикует запрос и
  возвращается, ничего не ожидая.
- **Внутреннее упрощение.** `inFlight` и `drained` удаляются вместе с их межпоточными
  инвариантами; TCS ожидания переезжает внутрь запроса закрытия (два параллельных
  `FlushAndCloseAsync` перестают затирать общий сигнал).

**Публичное API не меняется** — те же сигнатуры `Close()`, `FlushAndCloseAsync(CancellationToken)`,
`Dispose()`. Меняется только момент вызова `Disconnect` относительно возврата `Close()`.
`VersionPrefix` не меняется.

### Отклонение от формулировки задачи

Задача: «убрать флаги `closing`/`inFlight`/`drained`». `inFlight` и `drained` убираются
полностью. **`closing` убрать нельзя**: немедленное закрытие обязано *отбросить* уже стоящие
в очереди пакеты, а `FlushAndCloseAsync` — *доставить* их; оба закрывают порт сразу. При одном
читателе канала диспетчер, дойдя до пакета, стоящего в очереди **впереди** управляющего
сообщения, должен решить «доставить или отбросить» до того, как прочитает это сообщение —
значит, нужен внеполосный сигнал «идёт сброс». Три поля заменяются **одной** атомарной ссылкой
на запрос закрытия (несёт признак drain и TCS), без межпоточных инвариантов. Это меньше
подвижных частей, а не буквальное «ноль флагов»; наблюдаемое поведение от этого не зависит.

**Явно вне объёма:**

- смена сигнатур событий (`Action` → `Func<Task>`), async-потребление наружу;
- событийное чтение вместо таймера;
- шов/тесты — уже есть (`port-abstraction`); этот change опирается на них как на страховку;
- `VersionPrefix`.

## Capabilities

### New Capabilities

Нет.

### Modified Capabilities

- `packet-receiving`: требование «Закрытие адаптера и судьба очереди» меняется — `Disconnect`
  для немедленного закрытия становится асинхронным (порт закрыт по возврату, отключение — вскоре
  из потока доставки), гарантия «отключение последнее» усиливается до «обработчики начатого
  пакета доводятся до конца, затем отключение, после него — ничего», `Close()` из обработчика
  становится безопасным. `FlushAndCloseAsync` (ждёт остаток), отмена, запрет из обработчика —
  без изменений по смыслу.

## Impact

- **Код**: `MTRFXXAdapter.cs` — диспетчер (обработка запроса закрытия, отбрасывание/доставка
  остатка, вызов `Disconnect`), `Close` / `FlushAndCloseAsync` / `Dispose` (публикация запроса
  вместо прямой работы с очередью), удаление `inFlight` и `drained`, сведение `closing`
  к одной ссылке-запросу. Разбор пакетов, типизированные объекты, `SendCommand`, шов — не тронуты.
- **Публичное API**: без изменений; **меняется наблюдаемое поведение** `Close()` / `Dispose()` —
  `Disconnect` асинхронный.
- **Потребитель** (драйвер NooLite для `ThinkingHome.DeviceModel`): если он делал
  `adapter.Close()` и сразу считал адаптер отключённым, теперь должен ждать событие `Disconnect`.
  Проверить при интеграции.
- **Тесты**: 73 существующих — часть `CloseTests` меняет ожидания (`Disconnect` асинхронный,
  ждать через сигнал, а не сразу после `Close()`); добавляется тест на исправленный краевой
  случай (типизированное событие пакета доставлено до `Disconnect`) и на `Close()` из обработчика.
- **Документация**: `README.md` → «Закрытие» (асинхронность `Disconnect` у `Close`);
  `openspec/config.yaml` → `context` (снять пометку о краевом случае, обновить описание закрытия).
- **Проверка на железе**: регрессия `on`/`off`/`state`/`listen` на COM3 — порядок событий
  и `Disconnect` последним сохраняются.
