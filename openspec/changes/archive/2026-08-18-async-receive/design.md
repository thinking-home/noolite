## Context

Мотивация — `proposal.md` → «Why». Требования — `specs/packet-receiving/spec.md`,
`specs/command-sending/spec.md`. Здесь — как это устроить.

Текущий приём в `MTRFXXAdapter`:

```
System.Threading.Timer, каждые 50 мс, новый поток пула на каждый тик
  └─ TimerCallback
       └─ ThreadSafeExec(true, TryRead, Close)      ← lock (lockObject)
            └─ TryRead
                 while (BytesToRead >= 17)
                   ReadByte → маркер → Read(16)
                   Parse
                   ReceiveData?.Invoke            ← обработчик под замком
                   ветвление → типизированные события
```

Что важно для дизайна:

- `lockObject` — один на всё: `Open`, `Close`, `TryRead`, `SendCommand`. Обработчик, вызванный
  из `TryRead`, держит его целиком.
- `ThreadSafeExec` ловит исключение из `fn`, зовёт `errorHandler` (для `TryRead` — это `Close`!)
  и `Error`. То есть исключение в обработчике потребителя сегодня **закрывает адаптер**.
  Это стоит назвать: изоляция обработчиков — не только удобство, но и исправление.
- `System.Threading.Timer` не ждёт предыдущий колбэк: медленный обработчик копит потоки пула
  на замке.
- `ReceivedData` клонирует байты в конструкторе (`ReceivedData.cs:84`) — массив, положенный
  в очередь, никем дальше не разделяется.

Ограничение: шва над `SerialPort` нет (решение владельца — не вводить). Диспетчер юнит-тестами
не покрывается; проверка — DebugConsole на живом адаптере.

## Goals / Non-Goals

**Goals:**

- Обработчик события не держит `lockObject`; приём, отправка, закрытие от него не зависят.
- Порядок пакетов и последовательность обработчиков — как сейчас.
- Исключение в обработчике не роняет ни диспетчер, ни адаптер.
- Очередь ограничена, переполнение наблюдаемо.
- Два явных способа закрыть с разной судьбой очереди.

**Non-Goals:**

- Async-потребление (`IAsyncEnumerable`, `ChannelReader`) наружу.
- Смена сигнатур событий.
- Шов, юнит-тесты на диспетчер.
- Корреляция запрос↔ответ.
- Изменение `VersionPrefix`.

## Decisions

### 1. Очередь + один фоновый диспетчер, а не fire-and-forget

**Решение:** `Channel<byte[]>`; `TryRead` под замком только читает и кладёт; один фоновый
цикл `await reader.ReadAsync()` → `Parse` → события, вне замка.

**Альтернатива:** `Task.Run(() => ReceiveData?.Invoke(...))` на каждый пакет прямо из `TryRead`.

**Почему так:** fire-and-forget ломает порядок (пул не обещает FIFO — `toggle: 22` и `23` могут
поменяться местами, дедупликация по счётчику рушится) и запускает обработчики параллельно —
потребитель, писавший их в расчёте на последовательность, получит гонки в своём коде.
Один диспетчер сохраняет оба свойства и убирает ровно одно — замок.

### 2. В очереди — сырые `byte[17]`, не `ReceivedData`

**Решение:** `TryRead` выделяет `new byte[17]` на пакет и кладёт массив. Диспетчер делает
`Parse` и строит типизированные объекты.

**Почему так:** `Parse` уходит из-под замка вместе со всем остальным. Битый пакет (`Parse`
бросает на плохой рамке) сегодня роняет `TryRead` через `ThreadSafeExec` → `Close`; в диспетчере
он ловится как любое другое исключение → `Error` → следующий пакет. Один массив на пакет
обязателен: старый общий буфер `bytes` перезаписывался следующей итерацией `while`.
`ReceivedData` клонирует ещё раз — лишние 17 байт на пакет, не трогаем.

### 3. Bounded channel, ~~`DropOldest`~~ `DropWrite`, ёмкость из конструктора, по умолчанию 128

> **Пересмотрено после архивации (2026-08-18):** режим изменён с `DropOldest` на `DropWrite`.
> Аргумент «свежее состояние ценнее истории» неявно предполагал, что новый пакет — от того же
> устройства, что и вытесняемый. В очереди могут лежать пакеты от разных источников; вытеснение
> старого не «обновляет» состояние, а теряет чужое событие. Порядок прихода честнее: очередь
> сохраняет уже принятое, новое при переполнении отбрасывается. Основная спека `packet-receiving`
> и код обновлены; ниже — исходное решение как было.

**Решение (исходное):**

```csharp
public MTRFXXAdapter(string portName, int queueCapacity = 128)
// Channel.CreateBounded<byte[]>(new BoundedChannelOptions(queueCapacity)
// {
//     FullMode = BoundedChannelFullMode.DropOldest,
//     SingleReader = true,
//     SingleWriter = false   // TryRead из разных потоков пула, хоть и под замком
// }, itemDropped: _ => Interlocked.Increment(ref droppedPackets));
```

**Почему не `Wait`:** писатель — поток таймера под замком; ожидание места — та самая блокировка,
от которой уходим. **Почему не `DropWrite`/`DropNewest`:** свежее состояние блока или датчика
ценнее старого; терять новое ради истории — неправильный приоритет для протокола состояний.

**Optional-параметр** — старый вызов `new MTRFXXAdapter("COM3")` компилируется как есть.
Валидация: `queueCapacity < 1` → `ArgumentOutOfRangeException`.

**Счётчик, а не событие:** `public int DroppedPacketsCount => Volatile.Read(ref droppedPackets)`.
`itemDropped` вызывается из потока таймера под замком — там нельзя ничего долгого; инкремент —
можно. Событие с семи имеющимися — перебор; `Error` — не ошибка ввода-вывода. Дроп при ёмкости
128 и потоке «датчик раз в минуту» — симптом зависшего потребителя; счётчик для post-mortem
достаточен.

### 4. Изоляция обработчиков в диспетчере

**Решение:** каждый `?.Invoke` в диспетчере обёрнут:

```csharp
void Raise<T>(Action<object, T> handler, T arg)
{
    try { handler?.Invoke(this, arg); }
    catch (Exception ex) { RaiseError(ex); }
}

void RaiseError(Exception ex)
{
    try { Error?.Invoke(this, ex); }
    catch { /* обработчик Error бросил — глотаем, иначе диспетчер умрёт */ }
}
```

`Parse` — тоже под `try`: битый пакет → `RaiseError` → `continue`.

**Что меняется наблюдаемо:** сегодня исключение в `ReceiveData` через `ThreadSafeExec`
вызывает `Close()` — адаптер закрывается. Теперь — нет. Это исправление, а не регресс,
но в спеке зафиксировано.

### 5. Диспетчер — `Task.Run` в конструкторе, живёт до `Complete()` канала

**Решение:** запуск в конструкторе, а не в `Open()`. Один диспетчер на весь жизненный цикл
адаптера; `Open`/`Close` управляют портом и таймером, но не диспетчером. Диспетчер завершается,
когда канал `Complete()` и очередь вычитана — это делает `Dispose()` (и `FlushAndCloseAsync`).

**Почему не в `Open()`:** `Open`/`Close` могут вызываться многократно на одном адаптере
(это поддерживается сейчас: `ThreadSafeExec` с проверкой `IsOpen`). Перезапускать диспетчер
на каждый `Open` — лишняя сложность и лишний способ ошибиться (два диспетчера на один канал
= нарушение порядка).

**Что это значит для `Close()`:** он **не** завершает канал. Он останавливает таймер, закрывает
порт, **очищает** очередь (`while (reader.TryRead(out _))`), зовёт `Disconnect`. Диспетчер
остаётся ждать на `ReadAsync` — пустой, безвредный. Следующий `Open` — и он снова получает пакеты.

**`Dispose()`:** `Close()` + `writer.Complete()` + `timer.Dispose()`. Диспетчер увидит конец
и выйдет. `Dispose` не ждёт его — ждать нечего, очередь уже очищена `Close()`.

### 6. `FlushAndCloseAsync` — закрыть порт, дождаться очереди, `Disconnect`

**Решение:**

```csharp
public async Task FlushAndCloseAsync(CancellationToken ct = default)
{
    if (insideHandler.Value)
        throw new InvalidOperationException("нельзя ждать окончания обработки изнутри обработчика");

    // под замком: таймер стоп, порт закрыт — новых пакетов не будет
    // (то же, что Close(), но БЕЗ очистки очереди и БЕЗ Disconnect)
    ...
    // ждать, пока диспетчер не вычитает всё, что было
    await drained.WaitAsync(ct);          // drained — сигнал от диспетчера «очередь пуста»
    // теперь Disconnect
}
```

**Как диспетчер сообщает «пусто»:** после каждого пакета, если `reader.Count == 0`, сигналит
(например, `TaskCompletionSource`, который `FlushAndCloseAsync` создаёт перед ожиданием,
или `SemaphoreSlim`). Детали — при реализации; важно, что сигнал идёт **после** вызова
обработчиков последнего пакета, а не после его вынимания из очереди.

**Отмена:** `OperationCanceledException` из `WaitAsync` → очистить очередь → `Disconnect` →
пробросить. Порт к этому моменту уже закрыт.

**`Disconnect` — последнее событие в обоих способах.** Это инвариант, который потребитель
может использовать для сворачивания.

### 7. Защита от вызова из обработчика — `AsyncLocal<bool>`

**Решение:** диспетчер перед вызовом обработчиков ставит `insideHandler.Value = true`,
после — `false`. `FlushAndCloseAsync` проверяет флаг и бросает.

**Почему не по потоку:** диспетчер асинхронный, после каждого `await` он может проснуться
в другом потоке пула — «поток диспетчера» не определён. `AsyncLocal` течёт через `ExecutionContext`:
`await`, `Task.Run`, `ContinueWith` из обработчика — везде флаг стоит.

**Граница:** флаг течёт вглубь, но не назад. Обработчик, который сигналит через
`ManualResetEvent` в заранее живущий поток, где тот вызывает `FlushAndCloseAsync().Wait()`, —
не пойман. Это принятое ограничение: реальный случай («потребитель в обработчике решил закрыть
адаптер и синхронно ждёт») покрыт; экзотика — документируется, не ловится.

### 8. `SendCommand` из обработчика — работает, как и раньше

Обработчик теперь вне замка; `SendCommand` из него — обычный захват `lockObject`, без
реентерабельности. Поведение то же, что было, но по другой причине. Ничего делать не нужно,
зафиксировано, чтобы не искать.

### 9. Проверка — DebugConsole на живом адаптере

Юнит-тестов на диспетчер нет (нет шва). Режим `slow-handler` (рабочее имя) в DebugConsole:

- обработчик `ReceiveData` спит N секунд;
- параллельно из другого потока каждые ~200 мс шлётся `on`/`off` — с таймстампами;
- ожидание: отправка идёт с ровным интервалом, не проседая на N секунд, `Send_State`
  доходят до обработчика по порядку после сна.

Плюс `Close()` при непустой очереди (счётчик обработанных меньше принятых), `FlushAndCloseAsync`
(равен), переполнение (маленькая ёмкость + быстрый поток `Send_State` через `stress`-подобный
режим → `DroppedPacketsCount > 0`).

Что не проверить без шва: точное поведение при отмене `FlushAndCloseAsync` посреди обработчика,
изоляция при исключении в `Parse` (нужен битый пакет из порта). Первое — ревью кода, второе —
можно инъецировать битые байты в DebugConsole только если бы был шов. Принимается.

## Risks / Trade-offs

- **`Close()` теперь теряет данные по умолчанию** — осознанно (Decision 5/6). Потребитель,
  ждавший `Send_State` и вызвавший `Close()`, его не увидит. В doc-комментарии `Close()` —
  явная отсылка к `FlushAndCloseAsync`.
- **События приходят из другого потока, чем раньше** — не из пула таймера, а из потока
  диспетчера (тоже пул). Потребитель, синхронизировавшийся на конкретный поток, — не должен был.
- **`Task.Run` в конструкторе** — диспетчер стартует до `Open()`. Безвредно (ждёт на пустом
  канале), но объект с фоновой задачей до открытия — непривычно. Альтернатива (ленивый старт
  при первом `Open`) сложнее ради эстетики.
- **`AsyncLocal` не ловит все пути** к deadlock'у (Decision 7). Документируется.
- **Нет юнит-тестов на самую сложную часть change'а.** Диспетчер, дренаж, отмена — только
  ревью и e2e. Это цена решения «без шва», принята владельцем; ревью должно быть внимательным.
- **Порядок «`Disconnect` последний»** держится на том, что `Close()` очищает очередь под
  замком до `Disconnect`, а диспетчер между вынимаемым пакетом и вызовом обработчика не
  проверяет «закрыт ли адаптер». Гонка: диспетчер вынул пакет → `Close()` очистил остальное
  и позвал `Disconnect` → диспетчер вызвал обработчик для вынутого. Один пакет после
  `Disconnect`. Закрывается флагом `closing`, который диспетчер проверяет перед вызовом
  обработчиков; либо принимается как «не более одного пакета после Disconnect». **Решить
  при реализации; спека требует строгого «после Disconnect — тишина», значит флаг нужен.**
