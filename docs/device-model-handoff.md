# Handoff: ThinkingHome.NooLite ← нужды драйвера хаба device-model

Документ передачи контекста из сессии в репозитории `D:\Source\device-model` (2026-08-14).
Цель: в отдельной сессии (в этой папке) оформить и выполнить change по обновлению библиотеки
`ThinkingHome.NooLite`, чтобы на неё мог опереться драйвер NooLite для хаба device-model.

## Контекст

`ThinkingHome.DeviceModel` (репозиторий `D:\Source\device-model`) — нейтральная модель устройств
умного дома (структура повторяет Matter: Device → Endpoint → Capability/Property; протокол
Discovery / Query / Execute / Report) + хаб с плагинами-драйверами + адаптер Яндекс Алисы.
Первый реальный драйвер — **NooLite через адаптер MTRF-64-USB**.

Решения, принятые пользователем:

- Драйвер живёт в device-model отдельным проектом (по образцу `ThinkingHome.DeviceModel.Drivers.Stubs`)
  с **NuGet-зависимостью на `ThinkingHome.NooLite`**.
- Разделение ответственности:
  - **в библиотеке**: обновление до .NET 10; потокобезопасность отправки; обёртки
    `Read_State` / `Send_State` и async-API;
  - **в драйвере** (не здесь): корреляция запрос↔ответ и очередь команд; реконнект при пропаже USB;
    маппинг в нейтральную модель.
- Библиотека правится **в этой отдельной сессии со своей спекой** (OpenSpec уже инициализирован
  в этой папке: `openspec/`, команды `/opsx:*`).

Состояние репозитория: клон `thinking-home/noolite`, master `26ddc18` («reformat code & release 4.4
(dotnet 9)»), четыре проекта — `ThinkingHome.NooLite` (библиотека, ~700 строк), `.Console`
(dotnet tool `noolite`), `.DebugConsole`, `.Tests` (xUnit + FakeItEasy).

## Что нужно сделать в библиотеке

### 1. Обновление до .NET 10

Технически net9.0-библиотека подключается к net10.0-проекту как есть — обновление по желанию
владельца, но раз делаем, то целиком:

- `TargetFramework` → `net10.0` во всех четырёх `.csproj`;
- `System.IO.Ports` → 10.x;
- `global.json` → SDK 10.0.x;
- тестовые пакеты (`Microsoft.NET.Test.Sdk`, `xunit`, `xunit.runner.visualstudio`, `FakeItEasy`) — актуальные;
- `.github/workflows/dotnet.yml`: `dotnet-version: 10.0.x`, `-f net10.0`; `actions/checkout`, `setup-dotnet` — актуальные мажоры;
- `McMaster.Extensions.CommandLineUtils` в Console — проверить совместимость;
- `Package.xml`: `VersionPrefix` (5.0.0, если API меняется несовместимо; иначе 4.5.0), год в `Copyright`.

### 2. Потокобезопасность отправки

`MTRFXXAdapter.SendCommand` пишет в порт (`device.Write`) **вне `lockObject`**, под которым
идут `Open`/`Close`/чтение по таймеру. При нескольких устройствах на одном адаптере параллельные
вызовы могут перемешать байты 17-байтных пакетов. Нужна атомарная запись пакета.

Важная оговорка из протокола (см. ниже): lock закрывает только перемешивание байтов. Правило
«новую команду — только после ответа на предыдущую» требует сериализации на уровне «дождаться
ответа», а это слой корреляции — он по решению живёт в драйвере, **не** в библиотеке.

### 3. `Read_State` / `Send_State` и async-API

Сейчас в enum `MTRFXXCommand` есть `ReadState = 128`, `WriteState = 129`, `SendState = 130`,
но обёрток нет, а входящие данные доступны только через события `ReceiveData` /
`ReceiveMicroclimateData` (синхронно, из потока таймера).

Что нужно драйверу:

- **Обёртка `ReadState`** для nooLite-F: по каналу (ответят все привязанные блоки) и адресно по
  ID блока (`CTR=8`); параметр FMT — адрес строки таблицы состояния (0 — основная информация).
- **Разбор ответа `Send_State` с FMT=0** в типизированный объект (по образцу `MicroclimateData`):
  D0 тип устройства (SUF-1-300-A → 9), D1 версия прошивки, D2 состояние (биты 1–0: 00 выкл /
  01 вкл / 10 включён на время; бит 7 — сервисный режим), D3 мощность (реле: 100; диммер —
  последний уровень). Разбор ошибочного FMT (блок возвращает формат 255 на неизвестный адрес строки).
- **Async-приём**: поток входящих пакетов, потребляемый асинхронно (форма — на выбор в design:
  `IAsyncEnumerable<ReceivedData>`, `ChannelReader<ReceivedData>`, `IObservable` и т.п.), при этом
  **каждый пакет целиком** с полями Mode / Ctr(Result) / Togl(Remains) / Ch / Cmd / Fmt / D0–D3 / Id —
  драйверу нужны все, чтобы коррелировать ответы и отделять RX-пакеты датчиков.
- Опционально: `WriteState` (настройки блока, FMT 16/17/18) — не требуется драйверу на первом шаге.
- Именование: `ReceivedData.Remains` = байт TOGL из руководства (для TXF — сколько пакетов ответа
  осталось; для RX — счётчик новых команд). Стоит либо отразить в doc-комментариях, либо дать
  второе имя.

### Не делать в библиотеке (по решению — драйвер)

- Корреляция запрос↔ответ, очередь «одна команда в полёте», таймауты.
- Реконнект при пропаже/переподключении USB (в библиотеке есть события `Connect`/`Disconnect`/`Error`,
  переоткрытие — на потребителе).
- Модель устройств / маппинг в нейтральные типы.

## Факты протокола MTRF-64-USB-A (из руководства по эксплуатации)

Источник: https://noo.com.ru/f/rukovodstvo-po-ekspluatatsii-mtrf-64-usb-a_1.pdf?dl=1 (17 стр.).

- Пакет ПК→адаптер: `ST(171) MODE CTR RES CH CMD FMT D0 D1 D2 D3 ID0..ID3 CRC SP(172)`;
  ответ адаптер→ПК: `ST(173) MODE CTR TOGL CH CMD FMT D0..D3 ID0..ID3 CRC SP(174)`.
  CRC — младший байт суммы первых 15 байт. (Библиотека это уже реализует.)
- MODE: 0 nooLite TX, 1 nooLite RX, 2 nooLite-F TX, 3 nooLite-F RX, 4 сервисный, 5 обновление ПО.
- CTR при отправке: биты 5–0 — команда адаптеру (0 передать, 1 широковещательно, 2 считать
  буфер, 3 включить привязку, 4 выключить, 5 очистить ячейку, 6 очистить память, 7 отвязать адрес,
  8 передать по указанному ID nooLite-F); биты 7–6 — Nrep, число дополнительных повторов (0–3).
- **Адаптер отвечает на каждый принятый управляющий пакет.** CTR в ответе: 0 выполнена,
  1 **нет ответа от блока**, 2 ошибка, 3 привязка выполнена.
- **TOGL** в ответе: для nooLite-F TX — количество пакетов, которые осталось передать до завершения
  опроса канала (последний пакет серии → 0); для RX / RX-F — счётчик, увеличивается на единицу при
  приходе новой команды (передатчики повторяют пакеты — по TOGL дедуп).
- **Строгая последовательность:** «гарантированно передать новую команду можно только после прихода
  ответа от предыдущей» — одна команда в полёте.
- В nooLite-F TX после **любой** команды (вкл/выкл и пр.) блок присылает `Send_State` (130) с
  FMT=0 — то есть результат и свежее состояние приходят одним пакетом. `Read_State` (128) на канал →
  `Send_State` от **каждого** привязанного блока. Широковещательная команда (CTR=1) → после
  выполнения адаптер сам проверяет состояние блоков канала.
- Обычная передача (CTR=0) в nooLite-F идёт **по очереди каждому блоку канала**; CTR=8 —
  адресно по 32-битному ID блока. В ответах для F поле ID — адрес блока, который ответил.
- После подачи питания адаптер **12 секунд** в режиме обновления ПО; однократная передача MODE=4
  (в библиотеке `ExitServiceMode()`) переводит в рабочий режим сразу; в ответ приходит собственный
  nooLite-F адрес адаптера.
- Датчики (PT-111/PT-112 — `Sens_Temp_Humi` 21, FMT 7; PM — команды `On`/`Temporary_On`/`Off`;
  `Battery_Low` 20) — батарейные однонаправленные передатчики; приходят в режиме RX (MODE 1),
  привязываются к каналу адаптера (`CTR=3` в RX, окно 40 с). F-версий датчиков в каталоге нет.
- Классические силовые блоки nooLite (SU-1-x, SR-2-1000, SD-1/3-x) по-прежнему в производстве —
  однонаправленный TX (без ответа блока; адаптер всё равно отвечает пакетом о приёме команды).

## Проверка на живом железе

Первый шаг change по драйверу в device-model — проверка на реальном адаптере/устройствах:
в каком MODE приходят пакеты датчиков (ожидание — 1, RX) и является ли реле nooLite-F
(в ответе на команду TXF придёт `Send_State` с ID блока). Удобный инструмент —
`ThinkingHome.NooLite.DebugConsole` из этого репозитория (после перевода на .NET 10 — заодно
smoke-тест обновления). Имя порта на Windows — `COMx` (`SerialPort.GetPortNames()`).

## Как стартовать сессию здесь

1. Заполнить `openspec/config.yaml` → `context` (стек, ссылка на этот документ) — сделано из
   сессии device-model, проверить.
2. `/opsx:propose "обновить ThinkingHome.NooLite до .NET 10, потокобезопасная отправка,
   обёртки Read_State/Send_State и async-приём"` — далее ревью артефактов → `/opsx:apply` →
   релиз NuGet → `/opsx:archive`.
3. Порядок с драйвером — на выбор: сначала релиз библиотеки и драйвер на NuGet; либо драйвер на
   project reference с переключением на NuGet при релизе.
